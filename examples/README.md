# Examples

Two different things live here.

- **[`dump-graph.rs`](dump-graph.rs)** — a real Cargo example target. `cargo run --example dump-graph
  <path>` walks a checkout and prints its `Graph` as JSON. It is also what the container-backed test
  suites drive the crate with, so it stays honest.
- **[`apps/`](apps)** — a gallery of sample applications the extractor is pointed *at*. They are
  input, not code this crate builds (the workspace excludes them), and each ships with the graph
  `lci-codegraph` actually produces for it.

## The gallery

Every `graph.json` below is generated by this crate walking that application — never written by
hand — and `tests/examples.rs` regenerates and byte-compares all of them:

```bash
cargo test --test examples
```

```bash
UPDATE_GOLDEN=1 cargo test --test examples
```

That is the point of committing them. "Here is what the graph looks like for a Spring Boot app" is a
claim; a file a test regenerates is a fact, and it breaks loudly when the extractor drifts from what
the documentation shows.

## Reading the zeroes

Four of the seven columns above are mostly zero, and that is the most useful part of the table.

**Kotlin produces nothing at all.** Not a reduced graph — an empty one. There is no Kotlin grammar in
this crate, and `.kt` is not even in the extension fallback, so those files are skipped before
anything looks at them. That sample is committed *because* the answer is "nothing": a Kotlin Spring
Boot service is a very common thing to point a code-intelligence tool at, and an empty committed
graph answers "does this work on mine?" immediately instead of after an afternoon. It also hands
whoever adds the grammar a fixture whose expected output is already wired up.

**Route nodes are Spring-only.** NestJS's `@Controller('notifications')` / `@Get(':id')` and FastAPI's
`@app.get("/products/{sku}")` are structurally almost identical to Spring's annotations, and are
deliberately not extracted — so those apps show a resolved controller → service → repository call
chain and zero routes. Axum registers its routes with ordinary method calls on a `Router` rather than
with annotations, so there is nothing statically analogous to extract at all. Framework awareness is
one narrow, hand-curated allowlist, not a general capability, and these samples are what keeps that
scope statement from quietly becoming aspirational.

**The Keycloak sample is the negative case on purpose.** It is Java, but wired by a factory and a
`META-INF/services` file instead of annotations, so the framework pass stays completely silent while
ordinary cross-file Java resolution still works. Framework extraction is gated on file content — a
Spring import — not on "this file is Java".

## What the Spring samples do show

The two Java Spring apps are where the framework pass earns its keep. Between them they cover the
`@RequestMapping`-family argument shapes that occur in practice — a bare string, `path =`, `value =`,
a bare `@RequestMapping(method = ...)`, and an array of paths on one handler producing two route
nodes — plus a `@FeignClient` service boundary and a Spring Data derived query.

One detail in [spring-boot-maven-java](apps/spring-boot-maven-java) is worth reading the README for:
its repository declares only derived queries, so `findByCustomerEmail` resolves while the *inherited*
`save` and `deleteById` resolve to nothing and are not even nodes. Those methods are declared in a
dependency, not in the checkout. That is the honest boundary of an extractor that reads only the
source in front of it, and the sample is built to show it rather than to hide it.
